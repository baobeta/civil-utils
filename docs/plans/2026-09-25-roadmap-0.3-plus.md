# C3DTools roadmap 0.3 → 0.5 (after CTYTC)

> Status: proposal, 2026-09-25. Each item below becomes its own detailed plan (like `2026-09-24-tcvn-curve-elements.md`) when its release starts. Nothing here is committed to code yet.

**Goal:** cover the tasks a Vietnamese road/drainage engineer repeats every day where Civil 3D 2021 either has no feature or produces output that does not match Vietnamese drawing conventions (TCVN 4054, company templates, thuyết minh tables).

**How items were ranked.** Score = daily frequency (1–3) × gap in native Civil 3D (1–3) ÷ API risk (1–3). Ties broken by "reuses something we already built". Only items with score ≥ 2 are scheduled; the rest sit in the backlog.

Principles carried over from 0.2:

- **Parity first.** Where the office already has a working LISP or a drawing they trust, that is the reference and we reproduce it. Ask for the sample before planning.
- **Plain geometry before Civil 3D styles.** Drawing lines/text ourselves (as `CTYTC` does) is verifiable on any machine and never depends on unverified 2021 style APIs. Native styles come second, as an option.
- **Core does the math and text; the host only reads objects and writes entities.** Every table also exists as `TableData`, so CSV/XLSX/AutoCAD Table come for free.
- **One dialog per command, preview → confirm → one undo, XData tags so a rerun replaces its own output.** The `CurveDesignWindow` / `RouteWriter` / `YtcTag` pattern is the template.
- **Windows spike before any risky API.** Each release starts with a `CTSPIKE*` throwaway branch, as in 0.2.

## Release 0.3 — "hồ sơ hàng ngày" (target: 4 items, ~3 weeks)

### R1 · `CTFONT` — Font code conversion (TCVN3 / VNI-Windows / Unicode)

- **Why daily:** old drawings from partners arrive in TCVN3 (`.VnTime`, `.VnArial`) or VNI (`VNI-Times`); text shows as garbage until converted. Everyone has a LISP for this; most break on MText formatting codes or attributes.
- **Approach:** Core `VietFontCodec` with the three standard tables (TCVN3 ↔ Unicode, VNI ↔ Unicode) plus auto-detection by byte pattern; handles composed/decomposed forms and keeps MText control codes (`\P`, `\f…;`, `{…}`, `%%d`) intact. Host iterates `DBText`, `MText`, `AttributeReference`, `Dimension` text overrides, `Table` cells, `MLeader`; optionally changes the text style font to Arial/Tahoma. Selection or whole drawing; preview shows count per object type; one undo.
- **API risk:** low (all AutoCAD, no Civil). Spike: none.
- **Tests:** golden pairs for every Vietnamese letter (134 glyphs), MText with `\fVnTime|b0|i0|c0|p34;` preserved, round trip identity.
- **User provides:** 2–3 real legacy DWGs (TCVN3 and VNI) for acceptance.
- **Done:** all text in the sample DWGs readable; `U` restores; no `??` left.

### R2 · `CTTRACDOC` — Bảng trắc dọc kiểu Việt Nam

- **Why daily:** Vietnamese profile sheets carry a data table under the profile: cọc, khoảng cách lẻ, khoảng cách cộng dồn, lý trình, cao độ tự nhiên, cao độ thiết kế, chênh cao (đào/đắp), dốc dọc với chiều dài, cong đứng. Civil 3D bands can approximate this but the layout, fonts and rounding never match the company template, and band styles are hard to share.
- **Approach (plain geometry, parity with the office template):** select a profile view (+ the design profile); Core `ProfileTableBuilder` computes one column per station (all sample-line stations / cọc + geometry points + PVIs) with the rows above; host reads `Profile.ElevationAt(station)` for surface and design, draws the grid (lines) and text under the profile view using the view's own horizontal scale, on layers `TD_*`, XData-tagged for rerun. Row set, order, heights and decimals come from the preset (`ProfileTable` section) so each company keeps its template. CSV/XLSX of the same table via `TableData`.
- **API risk:** medium. Spike S1: `ProfileView.FindXYAtStationAndElevation`, `Profile.ElevationAt`, `ProfileView.StationStart/End`, `GraphStyle` horizontal scale in 2021; how to enumerate the alignment's stakes (reuse `RouteStakes` from 0.2 plus `SampleLineGroup` stations).
- **Tests:** Core table for a synthetic profile (two grades + one vertical curve), cumulative distances, cut/fill sign, rounding as in the template, culture-safe formatting.
- **User provides:** one finished profile sheet from a recent project (DWG or PDF) as the visual reference; the row list and order the office uses.
- **Done:** the generated table overlays the reference within text tolerance; rerun after moving a PVI updates it.

### R3 · XLSX export without third-party DLLs

- **Why now:** every table (curves, stakes, volumes, culverts, profile) ends up in Excel for thuyết minh/dự toán. Spike #7 showed ClosedXML fails inside Civil 3D 2021 (`System.Numerics.Vectors` binding), so XLSX was pushed to P1.
- **Approach:** Core `MinimalXlsxWriter` writing OOXML by hand (`System.IO.Compression` + XML: `[Content_Types].xml`, `workbook.xml`, one `sheet1.xml`, inline strings, numbers as numbers, a bold header row, column widths). No dependency. `TableData` → `.xlsx`. Add "Xuất Excel" beside "CSV" in every dialog.
- **API risk:** none (pure .NET). Tests: produced file opens in LibreOffice on CI (`soffice --headless --convert-to csv`) and round-trips the cells.
- **Done:** `CTYTCBANG`, `CTYTC` and R2/R4 write XLSX with Vietnamese headers that open in Excel with no repair prompt.

### R4 · `CTTOADO` — Bảng toạ độ cọc

- **Why:** site engineers need X, Y (and elevation) of every stake for setting out; usually typed by hand from the drawing.
- **Approach:** select alignment (+ optional surface/profile for Z); stations from `RouteStakes`/sample lines/user interval; host `Alignment.PointLocation`; Core formats `TableData` (Tên cọc, Lý trình, X, Y, Z); AutoCAD Table at a picked point + CSV/XLSX (R3). Optional: also place `COGO` points with the stake names.
- **API risk:** low; all members already verified in 0.2. Spike: none.
- **Done:** table matches the drawing to 0.001 m; rerun replaces.

### R5 · `CTCONGDUNG` — Đường cong đứng: khung yếu tố + kiểm tra TCVN

- **Why daily:** every profile PVI needs R, K, T, cao độ đỉnh, cao độ TĐ/TC, and a check against Rmin lồi/lõm and Lmin for the design speed. Civil 3D's PVI labels exist but, as with curves, don't match the TCVN box.
- **Approach:** mirror of `CTYTC` for profiles: read `Profile.Entities` (`ProfileTangent`, `ProfileCircular`/`ProfileParabolaSymmetric`), Core `VerticalCurveElements` (parabolic: K = L, T = L/2, external e = A·L/800…, plus circular variant used in VN practice), `VerticalCurveRuleChecker` from a `VerticalRules` preset table (Rmin lồi/lõm, Lmin per V, imax), box drawn in the profile view at the PVI with the 0.2 box style, table + XLSX. Redesign mode (edit R/L in a grid) only after the read-only mode works.
- **API risk:** medium. Spike S2: enumerate `Profile.Entities` types and PVI stations/elevations in 2021; `ProfileView.FindXYAtStationAndElevation` for placement.
- **User provides:** TCVN 4054 vertical tables (Rmin lồi, Rmin lõm, Lmin by V), like the Rmin table for 0.2 — no invented values.
- **Done:** numbers match a hand calculation for a two-grade fixture to 0.01; warnings appear for R below the table.

### R6 · `CTLAYER` — Layer standardisation from preset

- **Why:** drawings from partners/surveyors arrive with arbitrary layers; offices spend time mapping them to the company standard before anything else.
- **Approach:** preset `LayerMap` (pattern → target layer, colour, linetype, lineweight); host renames/moves entities, creates missing layers, reports counts; preview lists the mapping before applying; one undo. Optional purge of empty layers.
- **API risk:** low. Spike: none.
- **Done:** sample partner DWG ends with only standard layers; report shows what moved.

**0.3 Windows spike list:** S1 (profile view / profile API), S2 (profile entities). Both fit in one throwaway `CTSPIKEPROFILE` command; half a day.

## Release 0.4 — "trắc ngang và thoát nước" (~4 weeks)

### R7 · `CTTRACNGANG` — Bảng trắc ngang kiểu VN + xếp trang

- **Why daily:** cross sections are the bulk of a road hồ sơ. Each section needs the VN data block (cao độ tự nhiên/thiết kế, khoảng cách lẻ, diện tích đào/đắp, đánh cấp) and sections must be packed onto A3 sheets in station order with a title block.
- **Approach:** two commands. (a) `CTTRACNGANG`: for each `SectionView`, Core builds the data block from `Section` points (surface, design/corridor) and the material areas; host draws the block under the view (plain geometry like R2). (b) `CTXEPTRANG`: arrange section views into rows/columns per sheet size from the preset, add a sheet frame block and stamp sheet numbers.
- **API risk:** high. Spike S3: `SectionView`, `Section.GetSectionPoints`/`SectionPointCollection` in 2021, material sections (`QTO` remains corridor-bound per spike #5, so cut/fill area from surface vs design section polylines is our own computation, reusing `AverageEndArea` inputs), `SectionViewGroup` layout API vs moving views ourselves.
- **User provides:** one finished cross-section sheet as reference.

### R8 · `CTBANGCONG` — Bảng thống kê cống

- **Why:** every hồ sơ has the culvert schedule: lý trình, khẩu độ (D or B×H), chiều dài, cao độ đáy thượng/hạ lưu, độ dốc, loại cống, ghi chú.
- **Approach:** read `PipeNetwork` pipes/structures (fields verified in spike #6, wall thickness derived), intersect with the alignment for station/side, Core `CulvertTableBuilder`, table + XLSX. Shares fixture work with C-08 `CTCONG`.
- **API risk:** medium; needs the real-project pipe network fixture that Plan 2 already requires.

### R9 · `CTVN2000` — VN-2000 zone conversion

- **Why:** survey files come in a province's central meridian (e.g. 105°45' for Hà Nội, 107°45' for Đà Nẵng, 3° or 6° zones) and must be shifted to the project's meridian.
- **Approach:** pure Core: Transverse Mercator forward/inverse on the WGS-84 ellipsoid with VN-2000 parameters (k0 = 0.9999 for 3° zones, 0.9996 for 6°, false easting 500 000), meridian table of all 63 provinces in the preset; host transforms selected entities (points, polylines, blocks, text) or COGO points. Reference values from the Bộ TN&MT circular tables and a survey office's known control points.
- **API risk:** low; the math needs care. Tests: round-trip and published control-point pairs.
- **User provides:** at least 5 control points with coordinates in two meridians from a real project for acceptance.

### R10 · `CTMATDIA` — Surface cleanup and contour labels

- **Why:** after building a TIN, engineers delete long boundary triangles by hand and label contours one at a time.
- **Approach:** (a) delete triangles with any edge longer than a preset maximum, or outside a picked boundary (`TinSurface.DeleteLines`/`DeleteLine`, or add an outer boundary); (b) label major contours along a picked line at an interval (`SurfaceContourLabelGroup.Create` or plain text on the contour, parity with LISP habits).
- **API risk:** medium. Spike S4: `TinSurface` edge editing and contour label group creation in 2021.

**0.4 spike list:** S3 (section views), S4 (surface editing), plus the pipe-network fixture.

## Release 0.5 — "thiết kế sâu hơn" (~4 weeks, plan after 0.4 feedback)

- **R11** Superelevation + widening from TCVN tables written into the alignment (`SuperelevationCriticalStationCollection` — high risk in 2021, spike first) with the widening also feeding `CTYTC`'s Wb/Wl.

## Definition of done for every item

- Core logic unit-tested on macOS/CI; golden values from a trusted source (LISP, hand calculation, reference drawing).
- Command has a dialog (or a short prompt when there is nothing to configure), preview, cancel, single undo, XData-tagged output that a rerun replaces.
- Vietnamese messages, `InvariantCulture`, `CT` prefix, ribbon button, entry in `PackageContents.xml`, section in `docs/testing.md`, release notes line.
- No Autodesk DLL in the zip; no new third-party runtime dependency without a `THIRD_PARTY.md` entry (R3 exists precisely to avoid one).
